# Version del entorno que compilo firmware.bin / bootloader.bin / partitions.bin (original_laptop)

## CONCLUSION (2026-11-10, medido en la laptop)
El firmware original se reproduce con **platform espressif32 @ 7.0.1**
(framework-arduinoespressif32 @ 3.20017.241212 = **core Arduino 2.0.17**, ESP-IDF v4.4.7).
**NO con espressif32 @ 6.5.0** (core 2.0.14, ESP-IDF v4.4.6), que es lo que uso la Pi.
`platformio.ini` del proyecto quedo fijado en `platform = espressif32 @ 7.0.1`.

## Evidencia (main.cpp original sin parche, compilado en la laptop el 2026-11-10)

| Plataforma          | Core Arduino | String IDF en firmware.bin   | firmware.bin (bytes) | bootloader.bin / partitions.bin |
|---------------------|--------------|------------------------------|----------------------|---------------------------------|
| ORIGINAL (2026-11-02) | ?          | esp-idf: v4.4.7 38eeba213a   | 283408               | (referencia)                    |
| espressif32 @ 7.0.1 | 2.0.17       | esp-idf: v4.4.7 38eeba213a   | 283408               | SHA-256 IDENTICOS al original   |
| espressif32 @ 6.5.0 | 2.0.14       | esp-idf: v4.4.6 3572900934   | (no anotado; la Pi reporta 280832) | no comparados       |

- El core se leyo de `cores/esp32/esp_arduino_version.h` de cada paquete instalado (2.0.17 y 2.0.14).
- El string IDF se saco del propio binario (escaneo de strings ASCII).
- SHA-256 de bootloader.bin y partitions.bin recompilados con 7.0.1: iguales a los de
  `sha256sums.txt` (3d234a74... y 148b959c...).

## Limitaciones (no afirmar mas de esto)
- `firmware.bin` recompilado con 7.0.1 tiene el MISMO TAMANO y el mismo IDF, pero su SHA-256 NO
  es igual al original (ce3fa523... vs f221f1bd...). No se investigo byte a byte la diferencia.
  Causa probable, NO verificada: el binario lleva rutas de compilacion embebidas
  (`C:/Users/Libra/.platformio/...` en el original, `C:/Users/chees/...` en el recompilado) y el
  hash del ELF.
- El original se compilo bajo un perfil de Windows "Libra" que no existe en esta laptop: no se
  puede leer directamente que version tenia instalada. La conclusion es por reproduccion, no por
  lectura de ese entorno. Otras versiones con core 2.0.17 (p. ej. 6.9.x, 6.10.x) podrian dar lo
  mismo; no se probaron.
- No se probo en el ESP32: falta que la Pi compile con 7.0.1 y repita la regresion y la latencia.

## Que hacer en la Pi
1. `git pull` (trae `platformio.ini` con `platform = espressif32 @ 7.0.1`).
2. `pio run -e esp32dev` -> instala solo la plataforma 7.0.1 y el framework 3.20017.
3. Comprobar: `grep -a -o "esp-idf: v[0-9.]* [0-9a-f]*" .pio/build/esp32dev/firmware.bin`
   debe dar `esp-idf: v4.4.7 38eeba213a`.
4. Para restaurar el estado exacto de antes: flashear los 3 binarios de esta carpeta
   (bootloader 0x1000, partitions 0x8000, firmware 0x10000 -- offsets estandar de esp32dev en
   Arduino; VERIFICAR contra la salida de `pio run -t upload -v` antes de flashear).
5. Re-aplicar el parche v3 sobre esta base y repetir regresion + latencia: la degradacion de
   hoy (82/100, GET_POSITION 44 ms) se midio sobre core 2.0.14 y puede no repetirse.
